💡 Custom Action Aakhir Hota Kya Hai?

Sach bataun? Tum pehle din se Custom Actions use kar rahe ho! Jab tum workflow mein likhte ho: uses: actions/checkout@v3 ya uses: actions/cache@v3 — wo sab Custom Actions hi hain! Bas farq itna hai ki unko GitHub ki team ya community ne banaya tha.

Jab tum khud apna reusable step block banate ho (chahe YAML steps combine karke, ya JavaScript likh ke, ya Python/Docker mein wrap karke) aur usse uses: ./.github/actions/mera-action bol ke call karte ho — wahi Custom Action hai!

🧠 Simple Real-Life Analogy
JavaScript mein jab same 10 lines of code 4 jagah likhna padta hai, tum kya karte ho? Ek Function ya npm Package bana lete ho aur bas 1 line mein call kar dete ho!

Bilkul waise hi GitHub Actions mein jab same steps ya complex logic (jaise caching + install, ya AWS S3 deploy) bar-bar likhna pade, tum uska ek Custom Action (LEGO Block) bana lete ho aur workflow mein bas uses: se chipka dete ho!

⚔️ Reusable Workflow vs Custom Action — Farq Kya Hai?

Abhi tumne Section 06 mein Reusable Workflows padha tha. Dimaag mein aata hoga: "Bhai jab Reusable Workflow already code reuse karwa raha tha, toh Custom Action ki kya zaroorat thi?!"

🏗️ Reusable Workflow (workflow_call)

  • Scope: Poora JOB (ya multiple jobs) reuse karta hai.
  • Kahan call hota hai: jobs.<job-id>.uses: par.
  • Runner VM: Apni alag nayi VM pe chalta hai! Isliye file share karne ke liye upload-artifact / download-artifact lagta hai.
  • Language: Sirf YAML workflow syntax.
  • Analogy: 🏠 Poora alag kitchen hire kar lena.

🧩 Custom Action (action.yml)

  • Scope: Job ke andar ke STEPS reuse karta hai.
  • Kahan call hota hai: jobs.<job-id>.steps[].uses: par.
  • Runner VM: USI SAME VM mein chalta hai! node_modules ya ./dist directly agle step ko mil jaata hai — zero artifact overhead!
  • Language: YAML (Composite), JavaScript (Node), ya koi bhi language (Docker — Python, Go, Rust...).
  • Analogy: 🔌 Usi kitchen ke andar ka Mixer-Grinder!
✨ Golden Rule Yaad Rakhna
Socho agar cached-deps ko Reusable Workflow banate, toh wo alag VM mein npm ci karta aur VM delete ho jaati — lint job ko node_modules kabhi milta hi nahi! Isliye same job ke andar share hone wale steps = Custom Action!

🚨 #1 Beginner Mistake: Checkout Bhool Jaana!
Jab tum local custom action call karte ho (uses: ./.github/actions/cached-deps), toh usse pehle uses: actions/checkout@v3 chalana 100% COMPULSORY hai!
Kyun? Kyunki runner ek bilkul khaali Ubuntu VM hoti hai. Jab tak tum repo checkout nahi karoge, VM ke disk pe ./.github/actions/... folder exist hi nahi karega aur workflow turant crash ho jaayega!
(Note: Public/external actions jaise actions/cache@v3 ke liye checkout nahi chahiye kyunki GitHub unhe directly unke remote repo se download kar leta hai.)

Type 1 · Sabse Aasaan & Most Common

🧩 Composite Action: cached-deps

Socho tumhare workflow mein 2 steps har job mein repeat ho rahe the: Step 1: actions/cache@v3 se node_modules dhundho. Step 2: Agar cache miss hua, toh npm ci chalao.

Composite Action bolta hai: "Bhai in dono steps ko uthao aur ek .github/actions/cached-deps/action.yml mein pack kar do!"

03 Finished Project/.github/actions/cached-deps/action.yml
name: 'Get & Cache Dependencies'
description: 'Get the dependencies (via npm) and cache them.'

# 1️⃣ INPUTS: Caller 'with:' se value bhej sakta hai
inputs:
  caching:
    description: 'Whether to cache dependencies or not.'
    required: false
    default: 'true'   # ⚠️ Note: Inputs hamesha STRING hote hain!

# 2️⃣ OUTPUTS: Action se caller ko wapas jaane wali value
outputs:
  used-cache:
    description: 'Whether the cache was used.'
    value: ${{ steps.install.outputs.cache }}  # ← Composite me 'value:' MANDATORY hai!

# 3️⃣ RUNS: Engine = composite (multiple steps ka bundle)
runs:
  using: 'composite'
  steps:
    - name: Cache dependencies
      if: inputs.caching == 'true'
      id: cache
      uses: actions/cache@v3
      with:
        path: node_modules
        key: deps-node-modules-${{ hashFiles('**/package-lock.json') }}

    - name: Install dependencies
      id: install
      if: steps.cache.outputs.cache-hit != 'true' || inputs.caching != 'true'
      run: |
        npm ci
        echo "cache='${{ inputs.caching }}'" >> $GITHUB_OUTPUT
      shell: bash   # 🚨 Composite action ke har 'run:' step me MANDATORY!
shell: bash

Composite Action ka #1 Rule: Normal workflow mein GitHub automatically default shell le leta hai, lekin Composite Action mein har run: step pe shell: bash (ya pwsh/sh) likhna zaroori hai, warna syntax error aayega!

outputs.used-cache.value

Output Wiring: Composite action mein outputs ke andar value: field likh kar batana padta hai ki kaunse internal step ka output bahar bhejna hai (${{ steps.install.outputs.cache }}). (JS aur Docker actions mein value: nahi likhte — wahan code khud output set karta hai!)

inputs.caching == 'true'

Strings Only: Custom Action ke inputs hamesha strings hote hain. Isliye 'true' aur 'false' quotes mein compare karte hain!

Type 2 · Fast, Programmable & Cross-Platform

⚡ JavaScript Action: deploy-s3-javascript

Ab aate hain deploy job par! Humein built website (./dist folder) ko AWS S3 bucket pe upload karna hai aur live website ka URL wapas return karna hai.

YAML/bash mein complex logic, loops, validations, ya API calls likhna ganda ho jaata hai. Isliye GitHub bolta hai: "Direct Node.js mein JavaScript file likho — main usse runner pe directly execute kar dunga!"

.github/actions/deploy-s3-javascript/action.yml
name: 'Deploy to AWS S3'
description: 'Deploy a static website via AWS S3.'

inputs:
  bucket:
    description: 'The S3 bucket name.'
    required: true
  bucket-region:
    description: 'The region of the S3 bucket.'
    required: false
    default: 'us-east-1'   # Caller na de toh default use hoga!
  dist-folder:
    description: 'The folder containing the deployable files.'
    required: true

outputs:
  website-url:
    description: 'The URL of the deployed website.'
    # 👀 Notice! Yahan 'value:' NAHI hai — main.js khud core.setOutput() se set karega!

runs:
  using: 'node16'   # 💡 Modern GitHub Actions me 'node20' use karo (node16 deprecated hai)
  main: 'main.js'   # ← Entry point JS file!
.github/actions/deploy-s3-javascript/main.js
const core = require('@actions/core');
// const github = require('@actions/github');  // GitHub API & PR/repo context ke liye
const exec = require('@actions/exec');

function run() {
  // 1️⃣ Caller ke 'with:' inputs ko read karo
  const bucket = core.getInput('bucket', { required: true });
  const bucketRegion = core.getInput('bucket-region', { required: true });
  const distFolder = core.getInput('dist-folder', { required: true });

  // 2️⃣ Runner par AWS CLI command execute karo (aws ubuntu-latest pe pre-installed hai!)
  const s3Uri = `s3://${bucket}`;
  exec.exec(`aws s3 sync ${distFolder} ${s3Uri} --region ${bucketRegion}`);

  // 3️⃣ Output set karo (internally $GITHUB_OUTPUT me likhta hai!)
  const websiteUrl = `http://${bucket}.s3-website-${bucketRegion}.amazonaws.com`;
  core.setOutput('website-url', websiteUrl);
}

run();

Most Confusing Question Answered!

🤯 Wait... node_modules/ Repo Mein Commit Kyun Hai?!

Agar tumne 03 Finished Project/.github/actions/deploy-s3-javascript/ khola hoga, toh dekha hoga ki wahan node_modules/ folder pada hai! Normally hum node_modules ko .gitignore karte hain — fir yahan kyun?!

⚡ Reason: GitHub npm install KHUD NAHI CHALATA!
Jab GitHub Actions tumhara JS Action run karta hai, wo seedha node main.js execute karta hai. Wo tumhare action folder mein npm install nahi chalata! Agar @actions/core us folder mein nahi mila, toh turant Error: Cannot find module '@actions/core' aayega!

Option A: Course Approach (Simple)

node_modules/ ko git repo mein commit kar do (exclude mat karo). Learning & small local actions ke liye quick aur easy hai.

Option B: Production Best Practice ⭐

@vercel/ncc tool use karo: npx ncc build main.js -o dist. Ye poora code + saare node_modules ko EK single file dist/index.js mein bundle kar deta hai! Fir action.yml mein main: 'dist/index.js' set karo — repo bilkul clean rehta hai!

COPY requirements.txt /requirements.txt
RUN pip install -r requirements.txt  # 2. boto3 (AWS Python SDK) install karo

CMD ["python", "/deployment.py"]     # 4. Container start hote hi script chalao!
.github/actions/deploy-s3-docker/deployment.py
import os
import boto3
import mimetypes
from botocore.config import Config


def run():
    # 1️⃣ MAGIC! GitHub YAML 'with:' inputs ko INPUT_<UPPERCASE> env vars bana deta hai!
    bucket = os.environ['INPUT_BUCKET']
    bucket_region = os.environ['INPUT_BUCKET-REGION']
    dist_folder = os.environ['INPUT_DIST-FOLDER']

    # 2️⃣ AWS S3 client banao (AWS_ACCESS_KEY_ID & SECRET env se auto-load hoti hain!)
    configuration = Config(region_name=bucket_region)
    s3_client = boto3.client('s3', config=configuration)

    # 3️⃣ ./dist folder ki saari files walk karke S3 pe upload karo (correct Content-Type ke saath!)
    for root, subdirs, files in os.walk(dist_folder):
        for file in files:
            s3_client.upload_file(
                os.path.join(root, file),
                bucket,
                os.path.join(root, file).replace(dist_folder + '/', ''),
                ExtraArgs={"ContentType": mimetypes.guess_type(file)[0]}
            )

    # 4️⃣ Output wapas bhejo — $GITHUB_OUTPUT file container ke andar mounted hoti hai!
    website_url = f'http://{bucket}.s3-website-{bucket_region}.amazonaws.com'
    with open(os.environ['GITHUB_OUTPUT'], 'a') as gh_output:
        print(f'website-url={website_url}', file=gh_output)


if __name__ == '__main__':
    run()

Bridge 1 · Inputs

Docker container ke andar @actions/core nahi hota! Isliye GitHub har with: input ko UPPERCASE + INPUT_ prefix laga ke environment variable bana deta hai. Example: bucket-region → INPUT_BUCKET-REGION (hyphens hyphens hi rehte hain, spaces _ ban jaate hain!).

Bridge 2 · Files

GitHub runner ka poora repo folder (jisme tumne ./dist download kiya tha) container ke /github/workspace mein bind-mount hota hai — aur wahi default working directory hoti hai! Isliye Python mein os.walk('./dist') seedha tumhari built React/Vite files dekh paata hai!

Bridge 3 · Outputs

Runner ki $GITHUB_OUTPUT file bhi container mein mount hoti hai. Python usme website-url=http://... append kar deta hai, aur container band hone ke baad workflow use ${{ steps.deploy.outputs.website-url }} se padh leta hai!

⚠️ Docker Action Ke 2 Trade-offs Yaad Rakhna!
1. Linux Runners ONLY: Docker Container Actions sirf ubuntu-latest (Linux) runners pe chalte hain — macos-latest ya windows-latest pe FAIL ho jaayenge!
2. Slower Startup: Har workflow run mein GitHub Dockerfile se image build karta hai (pip install boto3 etc. — 15-40 sec extra). Speed badhani ho toh pre-built image Docker Hub / GHCR pe push karke image: 'docker://user/s3-deploy:1.0' use karo!

          Interview & Production Checklist
          
🧠 6 Golden Rules (Kabhi Mat Bhoolna!)

          

            

              Rule 1
              
Local Action = Checkout First: uses: ./.github/actions/... se pehle actions/checkout zaroor chalao.

            

            

              Rule 2
              
Composite = shell: bash + outputs.<name>.value: Har run: step pe shell dena compulsory hai, aur action outputs mein value: map karna compulsory hai.

            

            

              Rule 3
              
JavaScript = Bundle Dependencies: GitHub npm install nahi chalata! @vercel/ncc se bundle karo ya node_modules commit karo. Modern workflows mein using: 'node20' use karo.

            

            

              Rule 4
              
Docker = INPUT_ Env Vars + Linux Only: Inputs container mein INPUT_<UPPERCASE> env vars ban ke aate hain. Sirf Linux runners pe chalta hai.

            

            

              Rule 5
              
Secrets Kabhi Hardcode Mat Karo: Secrets ko caller workflow se env: ya with: ke through pass karo (jaise AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}).

            

            

              Rule 6
              
Decision Shortcut: Sirf YAML steps combine karne hain → Composite. Programming logic chahiye & JS aati hai → JavaScript. Python/Go/Rust ya custom OS environment chahiye → Docker.
